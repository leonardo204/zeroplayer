각 마일스톤에 완료 기준을 붙인다. 기간은 적지 않는다.

- [x] 1.x 저장소에서 `인증서/` 삭제, `.gitignore` 에 인증서 확장자 추가. 들어 있던 인증서는 2022년에 만료된 것이라 폐기 절차 없이 삭제만 했다
- [ ] 유출된 YouTube API 키 폐기 (Google Cloud 콘솔). 키는 만료가 없으니 이건 반드시 한다
- [x] `/Users/zerolive/work/zeroplayer` 저장소와 `project.yml` 작성
- [x] 빈 SwiftUI 앱이 빌드되고 탭 5개 껍데기가 보인다 (시뮬레이터 확인)

**완료 기준** — YouTube 키가 폐기됐고, 키체인의 Apple Development 인증서로 빈 앱이 실기기에 올라간다.

## M1 — 재생이 된다

프록시 없이 하드코딩된 방송국 몇 개로 재생 경로부터 완성한다. 여기가 앱의 심장이라 먼저 단단하게 만든다.

- [x] `AudioPlayerService` — 재생·일시정지·정지. 다음·이전은 자리만 두고 M3 에서 채운다
- [x] `AudioSessionManager` — `.playback`, 인터럽트 처리
- [x] `NowPlayingCenter` — 잠금화면 정보와 원격 명령
- [x] 미니 플레이어와 전체 재생 화면
- [x] 스트림 실패 감지 (15초 무응답)
- [x] ICY 메타데이터(곡명) 수신 실측
- [x] 평문 HTTP 스트림 실측
- [ ] 실기기 확인 — 백그라운드 30분, 전화 인터럽트, 잠금화면 조작

### 실측 결과 (2026-09-23, iPhone 17 Pro 시뮬레이터 / iOS 26)

**ICY 곡명은 방송국마다 갈린다.** Radio Paradise 는 곡명과 앨범 이미지 주소를 주고,
SomaFM 은 100초 동안 아무것도 주지 않았다. curl 로 `Icy-MetaData: 1` 을 보내면 SomaFM 도
헤더를 내주니 서버가 아니라 AVPlayer 쪽이 못 꺼내는 것이다. 헤더를 직접 넣어도 결과가 같았다.
방송국별 비율은 표본이 5개뿐이라 숫자를 적지 않는다. M2 에서 radio-browser 목록이 들어오면
그때 센다.

곡명을 앱에서만 얻는 계획은 절반만 된다. M2 에서 프록시가 서버에서 ICY 를 읽어 내려주는 안을
같이 검토한다.

**평문 HTTP 스트림은 재생되지 않았다.** `NSAllowsArbitraryLoadsForMedia` 를 켜도 `-1022`
(ATS 가 보안 연결을 요구함)로 막힌다. `NSAllowsArbitraryLoads` 까지 켜도 같았다. 같은 주소를
curl 로 부르면 200 이 온다. 시뮬레이터만의 동작일 수 있어 실기기에서 다시 잰다.

**완료 기준** — 화면을 끄고 주머니에 넣어도 30분 이상 끊기지 않는다. 전화를 받고 끊으면 재생이 이어진다. 잠금화면에서 일시정지·재생이 된다.

## M2 — 프록시와 데이터

- [x] Worker 배포, D1 스키마 적용 — `zeroplayer-api`, 라우트 `ai.zerolive.co.kr/zp/v1/*`
- [x] radio-browser 동기화 — 한국 114개 + 14개국 인기순, 모두 2,845개
- [x] `GET /stations`, `/stations/{id}/stream`, `/stations/facets`, `POST /stations/{id}/report`
- [x] 태그 정규화 배치 (규칙 + Workers AI `llama-3.3-70b-instruct-fp8-fast`)
- [x] 스트림 생사 점검 배치 (매시 150건, IP 주소는 판정 보류)
- [x] 앱: 탐색 탭, SwiftData 캐시, 오프라인 폴백

**완료 기준 — 채웠다.** 앱 소스에 스트림 주소가 없다(`zerolive.co.kr` 외 도메인 0건).
프록시에 닿지 못하면 캐시 50건이 그대로 보인다. D1 에서 방송국 한 줄을 지우니 목록에서 사라졌다
(엣지 캐시 때문에 최대 5분 걸린다).

여기서 드러난 것은 `CONTEXT.md` 6번에 적었다. 평문 HTTP 35%, 한국 지상파 HLS 토큰 만료,
Cloudflare 의 IP 직접 접근 차단 세 가지다.

## M4 — 큐레이션 (완료)

- [x] 1단 규칙 (서버) — 상황별 태그·분위기·시간대 규칙. M3 에서 먼저 만들었다
- [x] 분위기 분류 — 태그가 있는 방송국은 규칙 표로, 태그가 없는 것만 Workers AI
- [x] 2단 추천 세트 배치 생성 — 조합 120개를 매일 04:00 KST 에 만들어 D1 에 넣는다
- [x] `GET /recommend` — 세트가 있으면 꺼내 주고 없으면 규칙 결과를 즉석에서 만든다
- [x] 3단 기기 개인화 재정렬 — `Personalizer` 의 점수식
- [x] `OnDeviceReasoner` — Foundation Models 가용성 확인과 폴백
- [x] 추천 탭
- [x] 프리셋의 "자동 선택" 소스도 같은 3단을 거친다

문구는 OpenRouter 대신 Workers AI 로 만든다(`CONTEXT.md` 6-4). 기기 모델은 순서를 정하지 않고
맨 위 한 건의 이유 한 줄만 쓴다.

**완료 기준** — 자주 넘긴 채널이 아래로 내려가는 것은 `Personalizer` 의 점수식이 맡는다.
시뮬레이터에서 M3 때 들은 방송국이 서버 순서보다 위로 올라오는 것을 확인했다(목록의 ↑ 표시).
Apple Intelligence 를 쓸 수 없는 기기에서도 추천 목록이 그대로 나오는 것도 확인했다 —
시뮬레이터가 바로 그 경우다.

은 그대로 주소를 준다. **실기기에서 12회 탭을 직접 눌러 보는 것은 아직 남았다.**

## 순서를 이렇게 잡은 이유

재생을 M1 에 둔 것이 중요하다. 1.x 의 가장 큰 문제가 재생 구조였고, 여기가 흔들리면 뒤의 전부가 흔들린다. 프록시보다 먼저 한다.

큐레이션(M4)을 팟캐스트(M5)보다 앞에 둔 것은 큐레이션이 이 앱의 차별점이기 때문이다. 방송국만으로도 큐레이션은 성립한다. 팟캐스트는 큐레이션 대상을 넓히는 일이라 뒤에 온다.

광고(M8)를 마지막에 둔 것은 광고가 붙기 전까지는 약관 위험이 없기 때문이다. 앞 단계에서 기능을 확정하고 마지막에 광고를 얹는다.

## 중간에 출시할 수 있는 지점

M4 까지 끝나면 **라디오 + 프리셋 + 타이머 + 큐레이션** 으로 앱이 성립한다. 알람과 팟캐스트 없이도 쓸 수 있다. 일정이 길어지면 여기서 2.0 을 내고 나머지를 2.1·2.2 로 나눈다.

다만 히든 라디오(M7)는 1.7 사용자가 이미 쓰던 기능이라 첫 출시에 반드시 넣는다. 빼고 올리면 기능 후퇴가 된다.
